# Private Scheduler Site candidate

The Site hosts only the phone dashboard, bounded status projection, command queue, and audit records. The Python scheduler, SQLite authority, Codex CLI, and loopback API remain on the owner's computer. `remote/bridge.py --site` makes outbound HTTPS requests. The private Site has the six expected D1 tables, exact owner ID, separate TOTP and agent secrets. Dummy phone control was exercised, then remote controls were disabled again. See `docs/INTEGRATION_VALIDATION.md` for hosted evidence.

The private Sites audience currently includes only the owner. A visitor request must carry a Sites-authenticated user ID matching `OWNER_SITE_USER_ID` or, where the hosted runtime supplies no ID, the exact Sites-authenticated email matching `OWNER_SITE_EMAIL`. The owner observed both ID and email in the hosted identity probe, so prefer the ID for owner configuration. A separate TOTP challenge is required for an application session and all remote control. The temporary read-only exception below uses only the exact owner identity and cannot write. The access-policy account ID is not assumed to equal the Site-local identity ID. A read-only `/setup/identity` route can reveal the actual supplied identity only while `IDENTITY_PROBE_ENABLED=true` and remote control is disabled; turn it off after setup. This diagnostic is not MFA or authorization acceptance. ChatGPT sign-in alone is not treated as MFA. Site service access for the bridge is separate from a human session and must be accompanied by the distinct `AGENT_TOKEN` credential. Never put Sites or agent tokens, TOTP seeds, Codex credentials, or local API credentials in source, prompts, or command lines.

The Site environment needs `APP_ORIGIN`, exactly one of `OWNER_SITE_USER_ID` or `OWNER_SITE_EMAIL`, `OWNER_TOTP_SECRET` (base32, enrolled privately in an authenticator), `AGENT_TOKEN`, and `REMOTE_CONTROL_ENABLED=false` initially. To enroll, temporarily set `TOTP_ENROLLMENT_ENABLED=true` with controls off; only the exact signed-in owner can open `/setup/totp`. In the authenticator app, add an account by manual setup key and choose time-based codes; then visit `/index.html` and enter the current code. The setup page closes after the first successful TOTP verification. Then remove the enrollment flag; the identity probe is already disabled. For the temporary read-only exception in `docs/SPEC.md` section 13, set `READONLY_TOTP_BYPASS_ENABLED=true` only while controls remain disabled. The exact signed-in owner then sees status without a TOTP code; all writes are rejected and the UI labels this mode. Setting `REMOTE_CONTROL_ENABLED=true` disables this bypass automatically and returns to TOTP-gated sessions. The local bridge additionally needs `SCHEDULER_SITE_ACCESS_TOKEN`, `SCHEDULER_REMOTE_AGENT_TOKEN`, and `SCHEDULER_CONTROL_TOKEN` in its environment. On Windows, `remote/site_bridge.ps1 -Action save` accepts one JSON line with `site_access` and `agent_token` on stdin and stores it in a user-scoped DPAPI file under ignored `runtime/`; `-Action run` loads those tokens, requires the local API's control token in the process environment, and starts the Python bridge. The `OAI-Sites-Authorization` header is sent only to the configured Site origin. The first D1 migration is `drizzle/0000_scheduler.sql`; later migrations must be append-only. The source bundler in `scripts/build.mjs` embeds the HTML, browser script, CSS, contract and Worker into the supported `dist/server/index.js` artifact.

Local diagnostics:

```powershell
cd C:\dev-codex\scheduler\sites\scheduler-dashboard
npm ci --ignore-scripts
npm run build
npm run validate
npm test
```

The tests inject identity headers and a SQLite adapter directly into the Worker. They do **not** verify Sites dispatch, real ChatGPT sign-in, hosted D1 migrations, actual MFA enrollment, service access, cellular reachability, or safe hosted CPU/quota behavior. Keep control disabled and do not deploy until those gaps are tested with dummy projects. Publication is a separately controlled step under `docs/SPEC.md` section 11.
